# 0203 · 核心引擎管线设计

- 日期：2026-10-01
- 状态：定稿（实施基准）
- 上游依据：0102（技术路线）、0202（存储）、ADR-3/4/5/6/11

## 1. Ingest 管线（索引写路径）

### 1.1 阶段机与 checkpoint

```
 [A 授权校验] → [B 扫描与变更检测] → [C 分块] → [D 抽取] → [E 归并] → [F 社区] → [G 摘要]
      │              │                  │           │          │          │
      └──────────────┴──── source.state 状态机持久化于每阶段之间 ────────┘
                    pending → chunked → extracting → extracted → merged（终态）
                    任意阶段失败 → failed / quarantined（可续跑）
```

- `AbortSignal` 贯穿 A-G；中断时当前文件事务回滚，`extraction_batch.status = 'aborted'`，下次 `graphrag_index` 从 `pending/chunked/extracted` 断点续跑；
- 恢复扫描（学 DSH-RAG）：启动发现 `running` 残留批次时标记 `aborted` 并对非终态文件重新校验。

### 1.2 阶段 A：授权校验

输入 `roots`（默认取配置 `roots`，缺省为空 → 直接返回"未授权目录"报告）：

1. 每条 root 做 `realpath` 规范化；
2. 必须落在配置授权的根前缀内（防符号链接逃逸）；
3. 应用排除模式表（0202 §7）；
4. 输出：规范路径集合 + 拒绝清单（进报告，不静默）。

### 1.3 阶段 B：扫描与变更检测

- walk（忽略隐藏目录与排除模式）→ stat + `sha256`；
- 与 `source.content_hash` 对比，产出三集：`new` / `changed` / `deleted`；
- `changed`/`deleted` 触发级联：其旧 mention/关系贡献删除（`ON DELETE CASCADE` + 关系 weight 递减），受影响实体标记"陈旧"。

### 1.4 阶段 C：分块

- 目标块 800-1200 token（估算：`ceil(chars/3.5)` + 语言修正）；
- 边界优先级：Markdown 标题 > 空行段 > 语义单元（`}` / 缩进回落）> 硬截断；
- 记录 `(start_line, end_line, start_col, end_col)` 供举证（0202 chunk 表）；
- 一期文本族：UTF-8 编码探测（BOM/UTF-8 校验失败则跳过并记 `skipped-binary`）；PDF/DOCX 留 `Parser` 接口二期（ADR-11）。

### 1.5 阶段 D：LLM 抽取（成本核心）

**Prompt 契约**（每 chunk 恰好一次调用，ADR 成本纪律）：

```text
系统：你是代码库知识抽取器。从给定文本块中抽取实体与关系。
实体类型（封闭集）：module, file, function, class, type, concept,
                   config, cli, api, external_dependency, test
规则：
- 只抽取文本中有明确依据的项；不确定就不抽（宁缺勿滥）
- 每项给 confidence ∈ {0.6, 0.8, 1.0}
- 关系类型（封闭集）：defines, uses, calls, imports, depends_on,
                     configures, tests, relates_to
输出：仅输出 JSON，无其他文本。模式：
{"entities":[{"n":"名称","t":"类型","d":"≤40字描述","c":0.8}],
 "relations":[{"s":"源名","r":"类型","o":"目标名","d":"≤40字描述","c":0.8}]}
用户：<chunk 文本，带文件路径与行列号头>
```

**输出处理**：

1. 剥离 markdown 围栏 / 前后杂文（常见于对话式模型）；
2. `JSON.parse` 失败 → 一次修复重试（把报错喂回去要求仅输出修正 JSON）；再失败 → **隔离区**（`PARSE_FAILED`）；
3. zod schema 校验（封闭类型集、字段形状）→ 不合规项逐条丢弃并计数（`SCHEMA_INVALID` 进隔离区留档）；
4. `confidence < 0.6` 的项丢弃（阈值进配置）。

**调用纪律**：走 `ctx.llm.stream()`，`RequestUserInput` 角色（非会话记录）；失败码路由——`RATE_LIMIT` 指数退避重试（≤3 次，学宿主 retry 语义但插件自管，因为 llm-retry 挂在 agent 步骤不覆盖辅助调用）；`CONTEXT_WINDOW_EXCEEDED` → 块再对半细分一次；其余失败 → 该文件 `failed`，批次继续（单文件失败不炸整批）。

### 1.6 阶段 E：实体归并与边聚合

- 规范化键：`norm_name = lowercase(trim(name))` 的去符号形态（驼峰拆分不动，交由 FTS trigram 兜底）；
- 已存在实体：别名表追加、description 拼接去重（保留最早 + 最高置信描述）、度数累加；
- 关系 upsert：`(src, dst, type)` 唯一键 → weight+1，confidence 取加权均值；
- 孤儿清理：度数归零且无 mention 的实体删除。

### 1.7 阶段 F：社区检测（LPA）

- 触发条件：本次批次 `applyExtraction` 引起的边变更数 / 总边数 > 阈值（默认 5%），否则跳过（批次报告说明 skipped-reason）；
- 算法：无向加权 LPA——初始标签 = 节点 id，迭代按 weight 多数投票，平票取最小标签（确定性），最多 30 轮或标签不变即收敛；
- 写回 `community` 表并计算**社区指纹**（成员规范名集合的排序 hash）；
- 指纹未变的社区：保留摘要；指纹变化超成员数阈值（默认 30%）→ 进 G 重算队列。

### 1.8 阶段 G：社区摘要（LLM）

每待重算社区一次调用：

```text
系统：你是知识库摘要器。基于以下实体、关系与关键原文片段，生成 ≤150 字的
社区主题摘要：该社区代表什么、内部主要关系、与外部的边界。仅输出 JSON：
{"summary":"...","top":["代表实体名", ...]}
用户：实体（名/类型/描述）列表 + top 边 + 每实体 1 条 mention 原文摘录
```

产物写 `community_summary`（二手信息标记随证据包透出，见 0204）。

## 2. 查询管线（读路径）

### 2.1 local 模式（关系性/具体问题，零 LLM）

```
输入 q（自然语言）
1. 种子命中：entity_fts（trigram，q 的 2-gram 与全词变体）+ chunk_fts 命中反查 mention
   → 种子实体集 S（≤ 12 个，degree 加权）
2. PPR：以 S 为种子，阻尼系数 0.85，迭代 ≤ 20 轮（收敛阈值 1e-6）
   → 全实体分值向量，取 top-K（K=25）
3. 证据组装（token 预算 ≤ 6000）：
   - top 实体：名/类型/描述（二手标记）
   - 实体间高频边（≤ 40 条，按 PPR 分×weight 排序）
   - 每 top 实体 top mention 的 chunk 原文切片（±10 行上下文，精确行列号）
   - 所属社区摘要（≤ 3 条，二手标记）
4. 输出 EvidencePack（结构见 0204）
```

### 2.2 global 模式（全局/架构问题，LLM 打分）

```
1. 若社区数 ≤ 8：全部摘要直接进证据包（零 LLM）
2. 否则 map：社区摘要按 10 个/批送 LLM——"该社区与问题的相关性 0-10 分 + 一句理由"
   （用宿主当前模型，maxTokens 收紧到 ~800/批）
3. reduce：按分值排序，取 top 5 社区 → 其摘要 + 代表实体 + 每社区 2 条 chunk 引用
4. QueryMeta 透出本次打分调用数与 token 数
```

### 2.3 traversal 模式（影响分析/链路，零 LLM）

```
输入：seed（实体名或别名）、direction(out|in|both)、hops(1..4)、
      relation_types?、max_nodes(默认 200，硬上限 500)
1. seed 解析（entity_fts 模糊 + 别名表；多命中时返回候选让 agent 选择）
2. BFS，边按 weight 排序剪枝，节点预算控制
3. 输出 Subgraph：节点（实体卡）+ 边 + 每边 1 条 mention 引用 + 截断标记
```

## 3. 治理管线

- `forget(file)`：级联删 chunk/mention，关系 weight 递减，孤儿实体清理，社区指纹失效重算（走审批门）；
- `forget(entity)`：实体 + 其全量关系 + 别名删除（mention 保留但悬空清理）；
- `forget(graph)`：整库重建（唯一全量重置路径）；
- 隔离区处理：`graphrag_status` 报告隔离计数；M2 起提供 `graphrag_index` 的 `retryQuarantined` 选项重放（自动升 model 或降块长）。

## 4. 并发与一致性

| 场景 | 策略 |
|---|---|
| 同工作区并发 index | 进程内 promise 链互斥（同 cwd 排队），第二个调用返回 `INDEX_IN_PROGRESS` + 进度 |
| index 与 query 并发 | WAL 读不阻塞；查询读到的是"上一次已合并批次"的一致快照（SQLite 事务语义天然保证） |
| 宿主重启中断 | 阶段 B 的恢复扫描收敛状态 |

## 5. 成本模型（进 IndexReport/QueryMeta 的字段）

| 操作 | LLM 调用 | 说明 |
|---|---|---|
| 首次索引 N chunk | N 次抽取 + M 次摘要（M=社区数） | 唯一大成本，审批门公示预估：`est = dirty_chunks × 单价` |
| 稳态重索引 | ≈ 变更 chunk 数 | hash 未变零调用 |
| local / traversal 查询 | 0 | 全本地 |
| global 查询 | ceil(社区数/10) | 摘要已缓存，仅打分 |

预估公式在审批卡 `displayReason` 中呈现（"预计 ~N 次 LLM 调用，涉及 X 文件"），成本前置可拒（学 automation 审批审计模式）。
