# 0102 · GraphRAG 技术原理与检索策略

- 日期：2026-10-01
- 状态：定稿
- 目的：阐明本项目采用的 GraphRAG 技术路线——它解决什么问题、核心机制是什么、我们裁剪什么、为什么

## 1. 为什么平铺 RAG 不够，GraphRAG 补什么

平铺 RAG（BM25/向量检索 + chunk 返回）的固有短板，恰好是编码 agent 任务推理的高频场景：

| 任务推理场景 | 平铺 RAG 的问题 | GraphRAG 的补位 |
|---|---|---|
| "X 模块和 Y 模块之间通过什么耦合？" | 关系性答案分散在多个 chunk，Top-K 召回凑不齐完整链路 | 关系边显式存在，多跳遍历直接走通 |
| "这个项目的整体架构/设计思路是什么？" | 全局性问题没有局部 chunk 能回答，Top-K 全是碎片 | 社区摘要给出分层全局视图 |
| "改这个函数会影响哪些地方？" | 影响面 = 图上的反向可达集，词法相似度召回不了语义上不相似但结构上强关联的节点 | 反向边遍历精确回答 |
| 跨别名/跨语言提问 | "登录" / "auth" / "鉴权" 词法不相似 | 实体归一合并后是同一节点 |

一句话：**平铺检索按"相似"召回，图谱按"关联"导航**。编码任务推理（影响分析、调用链、跨模块依赖、全局理解）本质上是关联性问题。

## 2. Microsoft GraphRAG 的标准形态（参照系）

标准 GraphRAG 管线（Microsoft graphrag 0.x 确立的形态）：

1. **分块**（chunking）：语料切成 ~1200 token 块；
2. **实体/关系抽取**：每个 chunk 一次 LLM 调用，按给定实体类型 schema 抽 `(实体, 描述)`、`(源实体, 关系, 目标实体, 描述, 强度)`，可含协变量（声明性陈述）；
3. **实体合并**：跨 chunk 同名/别名实体合并，描述合并、边聚合加权；
4. **社区检测**：Leiden 算法做**分层**社区划分（多层粒度）；
5. **社区摘要**：每社区一次 LLM 调用生成结构化摘要（层级 map-reduce：子社区摘要汇成父社区摘要）；
6. **检索双模式**：
   - **local search**：从查询识别种子实体 → 取实体描述 + 邻接边 + 关联 chunk + 关联社区摘要 → 组装上下文；
   - **global search**：查询对**全部社区摘要**做 map-reduce（每批社区摘要一次 LLM 打分，reduce 汇总），回答全局性问题；
7. 代价：索引期 LLM 调用量 = O(chunks) 次抽取 + O(communities) 次摘要，成本显著高于平铺 RAG。

## 3. graph-memory 验证过的轻量化变体

adoresever/graph-memory（633★）证明了另一条可行路线，把"重 LLM"的部分压到最少：

- 抽取只做 **SPO 三元组**（比 Microsoft schema 轻），每轮对话**一次**辅助调用；
- 社区检测用 **LPA（标签传播）**替代 Leiden——纯本地迭代计算，零 LLM 成本，复杂度近似线性，够用（社区只用于导航，不追求社会学意义上的最优划分）；
- 查询排序用 **PPR（Personalized PageRank）**：查询词命中实体为种子，在图上扩散，把"与问题实体结构相近"的节点排到前面——这本质上是**把 local search 的邻域扩展做成带衰减的排序**，且不需要嵌入向量；
- 词法召回用 SQLite **FTS5** 兜底，embedding 可选可降级。

两个变体的关键差异与我们的取舍依据：

| 维度 | Microsoft 形态 | graph-memory 形态 | 我们的取舍 |
|---|---|---|---|
| 抽取 schema | 实体+关系+协变量+描述 | SPO 三元组 | **折中：SPO + 关系类型 + 置信度**，无协变量 |
| 社区检测 | Leiden 分层 | LPA 单层 | **LPA 单层起步**，预留分层 |
| 社区摘要 | 层级 map-reduce LLM | 无摘要 | **有，单层一次 LLM**（global 模式必需） |
| 查询排序 | 图遍历 + 向量 | PPR + FTS | **PPR + BM25/FTS**，向量后置 |
| 索引成本 | 高 | 低 | 靠增量索引 + checkpoint 控制 |

## 4. 本项目采用的技术路线（结论）

### 4.1 索引期（离线，写路径）

```
授权目录扫描(防抖/恢复) → 变更检测(内容hash) → 分块
  → LLM 抽取(SPO+类型+置信度, 每chunk一次调用, 失败进隔离区)
  → 实体归一合并(规范化名+别名) → 边聚合加权
  → LPA 社区检测(本地计算) → 社区摘要(每社区一次LLM)
  → 全程文件级checkpoint, 可取消, 断点续跑
```

### 4.2 查询期（在线，读路径）

- **local 模式**（具体/关系性问题）：查询 → FTS5/BM25 命中种子实体 → PPR 扩散排序 → 取 top 实体的描述、邻接边、关联 chunk 原文、所属社区摘要 → 组装证据包返回。
- **global 模式**（全局/架构性问题）：查询 → 分批对所有社区摘要做 LLM 打分（map）→ 汇总排序（reduce）→ 返回最相关社区摘要 + 其代表实体与 chunk 引用。
- **traversal 模式**（影响分析/链路追踪）：显式起点实体 + 方向 + 跳数 + 边类型过滤 → BFS/DFS 遍历 → 返回结构化路径与子图，**不做 LLM 摘要**（让 agent 自己推理，工具只给结构化事实）。

### 4.3 证据纪律（贯穿性原则）

继承 graph-memory 的核心原则：**图谱只导航，原文才举证**。

- 一切实体/关系都带 `source_chunks` 引用（文件路径 + 行号/字符区间）；
- 工具返回的证据包中，图数据（三元组、摘要）用于让 agent 理解结构，最终引用必须指向 chunk 原文；
- 社区摘要标记为"模型生成的二手信息"，与原文引用分级呈现。

### 4.4 成本纪律

- 抽取调用数 = 变更 chunk 数（增量），稳态重索引趋近于零；
- 摘要调用数 = 受影响社区数（只在图结构变化超过阈值时重算）；
- local/traversal 查询**零 LLM 调用**（纯本地计算）；global 查询 = 社区摘要批次数（摘要本身已缓存，仅打分调用 LLM，可用小输出控制成本）；
- 全部 LLM 调用走宿主 `ctx.llm`，复用宿主已配置的 provider/凭据/重试体系，插件自带零凭据。

## 5. 明确不做（及理由）

| 不做 | 理由 |
|---|---|
| 嵌入向量（一期） | `ctx.llm` 的适配器未验证统一暴露 embedding 能力；graph-memory 与 DSH-RAG 的实践都表明词法+图结构已覆盖核心价值；按冻结评测纪律，向量只有赢过基线才进主干 |
| 上下文接管（自动历史压缩） | 我们的场景是"agent 推理时显式调用"，显式工具调用更可控；graph-memory 该特性绑定对话记忆场景 |
| 协变量抽取（claims） | Microsoft 形态的可选部分，编码场景价值密度低，schema 复杂度显著上升 |
| 对话记忆（从会话历史抽图） | 与 graph-memory 定位冲突且非本项目目标；语料图与记忆图的数据模型不同（chunk 来源 vs 轮次来源） |
| Leiden 分层社区 | LPA 单层 + 摘要已支撑 global 模式；分层留二期，存储模型预留层级字段 |

## 6. 风险与已知局限（技术层面）

- LLM 抽取质量是最大不确定项：缓解 = 置信度阈值 + 隔离区 + `graphrag_maintain` 重试工具 + 抽取 prompt 的实体类型 schema 收敛到编码领域（模块/函数/概念/配置/外部依赖等）；
- PPR 对"查询词与实体名不命中"的情况失效：缓解 = FTS5 前缀/模糊匹配 + 别名表 + agent 可用 `graphrag_graph` 从已知实体手动扩展；
- 社区摘要质量依赖社区划分稳定性：LPA 结果在增量更新后可能抖动，缓解 = 社区指纹缓存，仅当成员变化超阈值才重算摘要。
