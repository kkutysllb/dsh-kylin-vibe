# 0103 · 双引擎（dsh + QiLin）兼容性研究

- 日期：2026-10-01
- 状态：定稿
- 目的：论证"一份插件代码同时运行在 DeepSeek Harness（dsh）与 QiLin（麒麟）两个宿主"的可行性，固化兼容性边界与参照实现

## 1. 两个宿主的同源性

本地验证基线（均为 2026-10-01 时点的 checkout）：

| 宿主 | 本地路径 | 框架 | 插件模型 |
|---|---|---|---|
| DeepSeek Harness（dsh） | `/Users/libing/kk_Projects/deepseek-harness` | Cordis | everything-is-a-plugin |
| QiLin（麒麟） | `/Users/libing/kk_Projects/QiLin` | Cordis（源码以 Kylin 名义 vendor 进仓） | everything-is-a-plugin |

两者包结构高度同构（`packages/` 下 `core`、`llm`、`tools`、`storage`、`fs`、`hooks` 等同名包并列），插件开发文档目录一致（`docs/user/develop/{basic,framework,practice}`）。**插件形态完全一致**：TypeScript 模块导出 `name` / `inject` / `apply(ctx)`，能力通过 `ctx` 注册，`ctx.effect()` 管理生命周期清理。

这决定了双引擎兼容的主要风险不在插件 API，而在**包名与版本门**（见 §4）。

## 2. 本插件依赖的宿主服务面（两个宿主均已验证暴露）

| 服务（inject 名） | 用途 | dsh | QiLin |
|---|---|---|---|
| `tools` | 注册 agent 工具（`ctx.tools.register(def)`） | ✓ | ✓ |
| `llm` | provider 中立模型调用（`ctx.llm.stream(options)`） | ✓ | ✓ |
| `systemPrompt` | 注入能力公告段（何时用 GraphRAG） | ✓ | ✓ |
| `storageDomain` / 存储 | 持久化（本项目自管 SQLite，仅用其定位数据目录） | ✓ | ✓ |
| `webServer` | M3 可选 Web 面板挂载 | ✓ | ✓ |
| `tools/pre-execute` 事件 | `graphrag_index` / `graphrag_forget` 人工审批门 | ✓ | ✓ |

### 2.1 `ctx.tools.register(def)` 工具契约（以 dsh-kylin-automation 实测形态为准）

```ts
interface ToolDef {
  name: string
  description: string
  parameters: Record<string, unknown>        // JSON Schema
  output: {
    schema: Record<string, unknown>
    render(args: unknown, value: unknown): readonly { type: 'text'; text: string }[]
  }
  timeoutMs: number
  execute(args: unknown, exec: unknown): Promise<unknown>
}
```

作用域挂载：在 agent 的 scoped context 上注册，只有被挂载的 agent 看到工具：

```ts
const registered = scoped.ctx.effect(() =>
  defs.map(def => scoped.ctx!.tools.register(def)))
```

调用者身份从 `exec` 防御性解构（`callerFrom` 模式）：`sessionId`、`cwd`。

### 2.2 `ctx.llm.stream(options)` 模型调用契约

```ts
for await (const chunk of ctx.llm.stream({
  provider: 'deepseek-official',            // 宿主已配置的 provider 路由
  model: 'deepseek-v4-flash',
  messages: [{ role: 'user', content: [{ type: 'text', text }] }],
})) { /* block-start / text-delta / usage / finish */ }
```

- 每个流**恰以一个终止 `finish` chunk 结束**（成功 / `error` / `aborted`），消费方按稳定失败码路由（`NO_ADAPTER`、`MISSING_CREDENTIAL`、`RATE_LIMIT`、`CONTEXT_WINDOW_EXCEEDED` 等），绝不按报错文本路由；
- 用 `BlockAssembler` 把 chunk 组装成内容块；
- 服务无自有配置、无 provider 线协议码——**插件自带零凭据、零 provider 代码**，完全复用宿主的 provider/凭据/重试体系；
- 辅助调用的输出应使用 `RequestUserInput`（request-only 输入）而非伪造 durable message——抽取/打分属于"非会话记录"的辅助调用。

### 2.3 `tools/pre-execute` 审批契约（0.1.7 双面文案）

dsh 0.1.7 起 `ask` 决策拆成两个字段，旧宿主自动回落，天然向后兼容：

- `reason`：进审计记录的**审计文案**（locale 无关）；
- `displayReason`：`{ en: string; [locale: string]: string }`，审批卡按界面语言渲染的**本地化文案**。

## 3. 参照实现：dsh-kylin-automation 的双引擎模式

`/Users/libing/kk_Projects/dsh-kylin-automation`（v0.3.1，基线 kcoder/dsh 0.1.7-rc.2）已完整趟平双引擎发布路径，本项目直接沿用其模式：

### 3.1 package.json 双字段

```jsonc
{
  "dsh":   { "bundle": { "patch": "./cordis.patch.yml" }, "client": { /* M3 起 */ } },
  "qilin": { "bundle": { "patch": "./cordis.patch.yml" }, "client": { /* M3 起 */ } }
}
```

两个宿主各自读自己的字段，指向**同一份** `cordis.patch.yml`——配置即一份，打包分发按宿主字段。

### 3.2 零 `@deepseek-ai/*` 运行时导入

- 所有宿主能力经 `inject` 服务名（字符串）注入，运行时从 `ctx` 取；
- `peerDependencies` 全部声明为 `*`：0.1.7 的 peer 兼容门按 semver 校验 `@deepseek-ai/dsh*`，裸 minor（如 `^0.1.7`）反而会被 prerelease 判定拒绝；且 **QiLin 通道报告的运行时版本不保证是 dsh semver**，`*` 是唯一安全声明；
- 类型经 `src/types/dsh.d.ts` 环境声明垫片获得（只声明用到的成员，从框架源码核shape），无需 workspace link 到宿主 checkout 即可 typecheck + build。

### 3.3 工程流水线

| 环节 | 机制 |
|---|---|
| 构建 | `scripts/build.mjs`（esbuild）双 bundle，产物提交 `lib/`，安装期零构建（pnpm 无需构建许可） |
| 测试 | `node --import ./tests/register-dsh-stubs.mjs --import tsx --test tests/*.test.ts`，宿主桩注入使核心逻辑引擎无关可测 |
| 质量门 | `pnpm check` = typecheck + test + build |
| 冒烟 | `scripts/smoke-plugin.mjs` 加载插件验证注册面 |
| 分发 | npm 发布（版本号驱动更新检测）+ `sync:mirror` 同步到 `dsh-plugins` 镜像 monorepo + GitHub tag 直装 |
| 安装 | `dsh plugin --profile web add <npm|github|本地路径>`；QiLin 同理 `qilin plugin ...` |

### 3.4 宿主兼容性审计表（沿用其方法，本项目逐面复核）

0.1.7-rc.2 相对 alpha 的关键变化及本项目影响：

| 宿主面 | 0.1.7-rc.2 变化 | 对本项目 |
|---|---|---|
| peer 兼容门 | 启动/bundle 加载/安装三处强制校验 | peerDeps 全 `*`，放行 |
| `tools/pre-execute` 的 `ask` | `reason`（审计）+ `displayReason`（本地化）双字段 | 采用双字段写法，旧宿主自动回落 |
| 系统提示词/工具描述瘦身 | 参数级规则收进参数描述 | 工具描述遵循"短公告 + 参数描述承载规则"风格 |
| QiLin 版本报告 | 不保证 dsh semver | 不做宿主版本硬依赖，能力探测走服务存在性 |

## 4. 双引擎兼容边界（本项目结论）

1. **插件运行时只依赖 Cordis 服务契约**（§2 服务面），不 import 任何 `@deepseek-ai/*` / `@qilin/*` 运行时模块——两个宿主对这套契约的实现在我们使用的面上同构；
2. **GraphRAG 核心引擎（分块/抽取/图/社区/检索）零宿主依赖**，是纯 TypeScript 库——单测不碰宿主；
3. **宿主差异被压缩到一个适配文件**（工具注册、审批挂钩、公告注入、数据目录定位），双引擎差异在此吸收；
4. 数据目录约定：dsh 下 `$DSH_HOME/graphrag/`（无则 `~/.dsh/graphrag/`），QiLin 下按其宿主 home 约定（M3 验证时落定，适配层统一为一个 `resolveDataDir(ctx)` 函数）；
5. 验证矩阵：每次发布前在两个宿主各跑一遍冒烟（插件加载 → 工具注册面 → 一次最小索引+查询往返）。

## 5. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 宿主服务契约漂移（dsh/QiLin 迭代不同步） | 中 | 只用稳定服务名；垫片类型收紧从紧；冒烟矩阵双宿主必跑 |
| `node:sqlite` 在两宿主 Node 基线下的行为差异 | 低 | 两宿主均要求 Node ≥22.19（≥22.13 即含 `node:sqlite`）；启动时能力探测，缺失则明确报错而非崩溃 |
| QiLin 侧 peer 门/加载器差异 | 低 | automation 已在 QiLin 通道验证 `*` 声明可行；沿用其结论 |
| Web 面板（M3）client inject 面差异 | 中 | 延后到 M3 实测；面板为可选角色，不影响核心工具面 |
